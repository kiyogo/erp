# Database migration plan — initial audit

## Known state

- Legacy documentation and `legacy/api/db.mjs` describe SQLite/PostgreSQL support; exact production schemas and version history require source-level reconciliation.
- The Rust backend currently initializes a SQLite schema in `server/src/main.rs`; there is no PostgreSQL adapter or general legacy database importer.
- Narrow, ADMIN-only JSON importers now cover five Plans browser-local collections, employee bank-cache/profile rows with encrypted quarantine, and CRM supplier evaluations/customer feedback. These allowlisted slices are not a general DB migration or proof of full data parity.
- The finance bank-account schema is now installed by `server/src/finance.rs` with the legacy table/column names, opening-balance constraint, creator foreign key and bank/account indexes. Fresh `account_number` values are encrypted using the finance-domain envelope compatible with `legacy/api/crypto.mjs`; no existing finance data was imported or modified.
- Do not connect this audit or tests to a production database. Do not read secret values from `.env` files.

## Required inventory before implementation

1. Enumerate all legacy schema creation/migration statements, tables, columns, constraints, indexes, triggers and DB-specific behavior.
2. Identify any schema declared in `DATABASE_SCHEMA.md` but absent from executable migrations, and vice versa.
3. Map every target table/column to its legacy source, transformations, defaults and null semantics.
4. Track identifiers, foreign keys, soft-delete, audit/approval history, file references, version records and encrypted fields.
5. Identify SQLite/PostgreSQL compatibility differences and decide adapters without silently dropping supported deployment modes.

## Import tool acceptance

- Dry-run is the default and never mutates either database.
- Apply requires explicit source/target paths, a verified backup and a disposable test copy during development.
- Import is transactional/batched, resumable and idempotent; it preserves IDs and history or writes a verified mapping table.
- Verify compares row counts, uniqueness, foreign keys/orphans, soft-deleted rows, file checksums and business aggregates (including financial balances).
- Source is read-only. No production import is run by the coding agent.
- Logs and reports contain no credentials or sensitive row values.

## Finance bank accounts — schema and sensitive-field compatibility

- Legacy table: `finance_bank_accounts` in `legacy/api/db.mjs`; `account_number` is `UNIQUE`, `opening_balance` is non-negative, and `created_by` references `users`. The Rust startup schema preserves these fields and indexes.
- Legacy `GET/POST /finance/bank-accounts` is ADMIN-only. Rust preserves the camelCase account DTO and account-number encryption envelope. A Node-generated finance-domain fixture is decrypted in a Rust regression test; Rust writes are checked for ciphertext-at-rest and missing-key fail-closed behavior.
- Application-level duplicate plaintext detection runs inside an immediate SQLite transaction because randomized ciphertext makes the legacy `UNIQUE(account_number)` constraint insufficient to detect duplicate plaintext values. The SQL uniqueness constraint remains in place as a secondary safeguard.
- `balance` maps to the declared opening balance. It is not a verified bank balance. No real records, credentials, database, or encryption master key were accessed for this slice.

## Finance internal bank transfers

- The Rust schema adds `finance_bank_transfers`, with foreign keys to source/destination `finance_bank_accounts`, unique references to both cash-voucher IDs, actor/time attribution, and a unique `(created_by, idempotency_key)` constraint. Existing `finance_cash_transactions` rows are not altered.
- ADMIN-only `POST /api/v1/finance/bank-transfers` resolves stable account IDs to their canonical bank-name labels and atomically inserts the legacy-compatible outgoing `Chi`, incoming `Thu`, and link row. If either voucher or the link row fails, SQLite rolls back the whole operation.
- Same-key, same-payload retries return the original linked pair; same-key/different-payload requests conflict. Account references, same-account selection, amount range and note length are validated. Tests inject a failure on credit insertion and verify neither voucher nor transfer link remains.
- The operation deliberately does not infer live available funds from `opening_balance`, because that value is only a user-declared opening amount and no verified bank-feed/reconciliation exists. No legacy or production data was imported.

## Finance legacy data import

- `tools/export_legacy_finance.mjs` uses Node `node:sqlite` in read-only mode against an operator-provided SQLite copy, selects only `finance_bank_accounts` and `finance_cash_transactions`, and refuses to overwrite an existing output. Exported values may contain plaintext account numbers; the output must be treated as sensitive even when the source used ciphertext.
- The ADMIN-only Rust preview/apply contract preserves source IDs and finance fields, accepts bank and petty-cash vouchers, and deliberately does not invent transfer-link rows because the legacy schema has no stable relationship identifier. It requires the configured finance encryption key and encrypts account numbers for target storage; source-row archive content is encrypted as well.
- Preview is non-mutating and contains only counts, conflict counts, source identity, confirmation phrase and a digest over source plus target state. Apply rechecks that digest under an immediate transaction, maps creator identity to the importing ADMIN, writes audit/import rows and target records atomically, and rejects conflicts/stale plans.
- Exporter fixtures verify source row counts remain unchanged, allowlisting, output no-overwrite and sensitive/plaintext cases. Backend fixtures verify summary-only preview, role denial, encryption, replay, validation, stale-target rejection and rollback. No production database, key or finance record was used; live reconciliation and backup/restore rehearsal are still mandatory before any real import.

## Status

`PARTIAL IMPLEMENTATION`; selected localStorage domains have read-only exporters and digest-bound preview/apply importers. Synthetic fixture tests and Linux/WASM builds pass in Docker, but no real browser cache or production database was imported. Full database/schema reconciliation and PostgreSQL parity remain unimplemented.

## Legacy plan localStorage import slice

- `tools/export_legacy_plan_collections.js` reads only the five allowlisted `kiyovn_cache_<scope>` keys. It does not inspect `kiyovn_datastore_cache`, auth/session/token keys, other collections, or network APIs, and it never writes to legacy localStorage.
- The JSON bundle is capped at 7 MiB and 5,000 rows. `POST /api/v1/legacy-import/plan-collections/preview` validates each typed plan DTO and reports destination counts without mutation. `POST /apply` requires the previewed bundle hash and exact batch confirmation.
- Apply is ADMIN-only, uses an immediate SQLite transaction, refuses any included scope with existing target rows, preserves row keys and unknown JSON fields, and records a unique append-only batch/audit row in `legacy_import_runs`. A failed insert or audit write rolls back the entire batch. Replaying the same batch is rejected.
- This slice transfers browser-local plan records only. It does not import users, credentials, payroll, employee records, signatures, files/blobs, audit/workflow history, other collections, or an external SQLite/PostgreSQL database. It does not identify whether source values are demo or business data; review the source and preview before applying.
- Source remains read-only. Do not execute against production until a disposable-copy end-to-end import and backup/restore procedure have been verified. Empty-scope refusal is an intentional guard, not a merge or resume strategy.

## CRM supplier evaluations and customer feedback import slice

- `tools/export_legacy_crm_operations.js` reads only `kiyovn_cache_crm_supplier_evaluations` and `kiyovn_cache_crm_feedback`; it validates stable keys, writes a bounded JSON download, never changes localStorage, and does not log record contents. The feedback export is plaintext and may contain customer phone/contact/content; use only an approved transfer path and securely remove temporary files after verification.
- `POST /api/v1/legacy-import/crm-operations/preview|apply` is ADMIN-only, capped at 8 MiB/5,000 records, requires configured CRM encryption, and uses a digest over the submitted bundle plus destination fingerprints/outcomes. Apply requires the unchanged preview digest and exact batch confirmation and writes the records, encrypted raw-source provenance and append-only audit run in one immediate SQLite transaction.
- Supplier totals and tiers are recomputed by Rust from bounded score dimensions; unsupported/invalid decision values conflict rather than being trusted. Feedback phone is CRM-encrypted, and browser-supplied resolved status/date/actor are not trusted: imported feedback returns to `Đang xử lý` with no resolved date. Imported records carry `legacyImportStatus=unverified`; original source JSON is preserved only in encrypted provenance. Unknown non-audit business fields are retained.
- Stable origin+scope+source-key hashes make identical re-exports idempotent; changed source content under the same stable key conflicts. Preview reveals counts/hashes only. Synthetic tests cover ADMIN access, PII-free non-mutating preview, encryption/recalculation, confirmation/stale digest, rollback behavior and replay. No real localStorage, customer data, production key or database was accessed/imported; production operation and backup/restore rehearsal remain open.

## Broadcast slice note

The admin broadcast slice reuses the existing Rust `collection_records` table and `system_broadcasts` scope, preserving the legacy JSON field names; it adds no DB schema migration. New records are server-generated drafts with UUID-backed keys. Activation-email template JSON is stored under the existing `settings` table key `activation_email_template`; it contains no credentials. No legacy database or localStorage data was imported. Legacy broadcast payload variants and the full collection-table mapping still require inventory before a data-import tool is approved.

Meeting-room inventory and bookings likewise reuse `collection_records` scopes `meeting_rooms` and `room_bookings`, retaining legacy `key`/camelCase fields and unknown booking properties during cancellation updates. Booking conflict checks and inserts use an immediate SQLite transaction. This provides persistence within the Rust database but does not import records from a legacy browser `localStorage` or another production database.

Workflow blueprint catalog records reuse the existing `collection_records` scope `workflow_blueprints`, retaining the legacy camelCase DTO fields, nested approval steps and form fields. Typed create/status operations are transactional; generic writes are blocked. No browser `localStorage`/legacy collection import is performed, and the catalog does not create workflow instances or signatures.

Employee proposals use a dedicated `employee_proposals` SQLite table compatible with the legacy column names and constraints, plus submitter/status indexes and a case-insensitive unique code index. Submitter and reviewer IDs reference Rust `users`; employee code/name are read from `employee_profiles`/`users` for the wire DTO. Create and review use immediate transactions. The table is created with `IF NOT EXISTS`; no legacy database import is performed, and existing localStorage/legacy rows are not assumed to be present in this database.

Enterprise tasks use dedicated `tasks`, `task_checklist_items`, `task_comments`, `task_activities` and `task_reports` tables with user/task foreign keys, status/progress checks and lookup indexes. Task and child writes use SQLite transactions; deleting a task cascades to its children. Legacy's denormalized `users.employee_code` is resolved through Rust `employee_profiles`. Rust handler/integration tests now cover lifecycle, assignment authorization, task-scoped attachments and atomic single/multi-assignee creation; the workspace suite passes in Docker. No legacy task rows or browser-local records are imported, and a safe historical task importer remains open.

Typed workflow requests are stored in `collection_records` under `workflow_requests`; submission and ordinary decision events are appended to `workflow_request_events` in the same SQLite transaction as request creation/update. SQLite triggers reject UPDATE/DELETE of event rows; generic request reads require ADMIN and generic writes are blocked. Typed list/create/decision routes require ADMIN, and the creator cannot decide their own request. Non-PKI steps support approve/reject/return with actor/time/note history; PKI-required steps fail closed with 503 until a real signing provider exists. Attachments remain empty. This does not yet implement employee ownership/visibility, return/resubmission, approver assignment by department role, file ownership, policy/delegation settings, or legacy browser-storage import. The legacy signature/audit metadata is fabricated and must not be imported as verified records. Before any legacy data is applied, design and test a dry-run importer preserving real actor/time/decision history, ownership, state transitions and file references.

Attendance shift catalog records reuse the existing Rust `collection_records` table under `attendance_shifts`; no SQL schema change or legacy-data import has been performed. Rust uses the legacy full-collection `PUT` contract and replaces rows within a single SQLite transaction. The typed client preserves unknown JSON properties, but browser-local/legacy database rows have not been transferred. Concurrent stale collection writes and generic mutation audit parity remain open.

Typed assignment records use `attendance_shift_assignments` and `attendance_shift_assignment_events`, with employee/creator foreign keys, immutable employee and shift snapshots, case-insensitive unique assignment codes, effective-date checks, lookup indexes and append-only event triggers. Creation uses an immediate transaction and only references an active USER employee profile and active shift-catalog row. The legacy `attendance_shift_assignments` generic collection remains ADMIN-readable for review but generic writes are blocked; its free-text rows are not imported. A future importer must resolve employee and shift IDs unambiguously, retain IDs/codes and report unresolved rows without dropping them. Schema SQL/handler tests are source-only until the Rust toolchain is available.

The retained ADMIN legacy leave screen reuses `collection_records` under `leave_requests` and `employee_leaves`; its old rows have not been imported or reshaped. Rust validates payloads and preserves unknown fields/legacy aliases. Those generic scopes stay ADMIN-only because `collection_records` has no owner key. New employee self-service requests use dedicated `employee_leave_requests` rows with an FK to the authenticated user, immutable employee code/name/department snapshots, constrained status/date/day fields, owner/status indexes, and `employee_leave_request_events`. Submission and ADMIN decision event are stored transactionally; SQLite triggers reject event updates/deletes. The handler requires an active linked `employee_profiles` row, derives identity server-side, and does not trust client identity. No legacy data has been imported, no balance/deduction is modeled, and backend schema/handler tests remain unrun until the Rust toolchain is available.

New employee overtime submissions use separate `employee_overtime_requests` and `employee_overtime_request_events` tables, with user/reviewer foreign keys, immutable employee identity snapshots, owner/status indexes, a 0.5-hour minimum/step, constrained request category/status and append-only history triggers. No upper-hours rule is added because none is present in the audited employee form. Create and ADMIN decision plus event are transactional; the owner is derived from the authenticated user's active HR profile. No legacy overtime rows are imported. The fake legacy rate/pay calculation, monthly cap and attendance actuals are not represented as payroll data; a verified pay policy and timekeeping contract are still required. Rust schema/handler tests are source-only until the toolchain is available.

## CRM contacts slice

- Rust initializes `crm_contacts` with the legacy contact types, amount checks, timestamps, creator FK and type/name/code indexes. The PII columns `phone`, `email`, `address` and `bank_account` remain text columns but hold the same `ENC:{...}` envelope format; business name, tax code and amounts remain as defined by the legacy schema.
- Rust implements the legacy CRM derivation: HKDF-SHA256 with `kiyovn-salt-{version}` and `KIYOVN-Secure-Envelope-crm-data-{version}`, followed by AES-256-GCM with a fresh 12-byte nonce and base64url envelope fields. A fixed envelope generated with Node's `node:crypto` and an artificial test key is decrypted by a Rust test.
- Key resolution accepts `KIYOVN_MASTER_KEY`; the legacy `.kiyovn-master.key` file is read only when `KIYOVN_DATA_DIR` is explicitly configured. Rust does not generate a key file. Missing key prevents writes and prevents returning encrypted PII; malformed/authentication-failing envelopes return an error rather than ciphertext.
- `tools/export_legacy_crm_contacts.mjs` accepts only an explicitly supplied SQLite source path and stable source database ID. It opens SQLite read-only/query-only, allowlists the `crm_contacts` columns, caps the bundle at 5,000 rows/7 MiB and creates a new output file without overwrite. It exports encrypted source envelopes unchanged; it does not inspect `.env`, credentials, tokens, or decrypt contact PII. Use an approved disposable database copy, not a live production DB.
- ADMIN-only `POST /api/v1/legacy-import/crm-contacts/preview|apply` accepts the bounded bundle, validates legacy fields and decrypts/re-encrypts phone/email/address/bank account using the configured CRM key. Preview returns only counts, hashes and a confirmation phrase. Apply binds to the preview digest and exact phrase; it uses one immediate SQLite transaction, preserves contact ID/code/createdAt/updatedAt, maps `created_by` to the authenticated ADMIN, rejects target ID/code conflicts, and records append-only batch/source ledgers. The entire source contact row is encrypted in the provenance ledger. Repeated exact source rows are idempotent; changed payload under the same stable source database ID/contact ID conflicts.
- Imported contacts carry a derived `legacyImportStatus=unverified` marker in the contact API and UI. This is not a verified identity or approval. CRM key absence/authentication failures fail closed. Synthetic in-memory HTTP tests cover authorization, non-mutating/PII-free preview, encrypted storage/archive, actor mapping, preserved identifiers/timestamps, confirmation, re-export and changed-source conflict. No real legacy data has been imported; key provisioning, disposable-copy backup/restore rehearsal, operator review and any production run remain required.

## HR employee bank-account import slice

- `tools/export_legacy_employee_bank_accounts.js` reads only `kiyovn_cache_employee_bank_accounts`, writes no legacy storage, and exports a bounded bundle. The file contains plaintext account values; the shared admin migration screen warns operators to protect and remove it after reconciliation.
- ADMIN preview reads the bundle plus `collection_records.employee_bank_accounts` and bank fields inside `employee_profiles.details_json`; it returns summary counts/hash only, not account values. The hash binds the source snapshot and canonical profile resolution so a changed source requires a fresh preview.
- Apply requires the preview hash and exact batch confirmation, uses an immediate SQLite transaction, and is idempotent by hashed source kind/origin/key. It never changes the old generic collection. Directory-linked rows are encrypted and inserted with pending status and non-primary state; source approval/identity claims are not trusted. Unknown, duplicate or unlinked records are retained in append-only encrypted quarantine rows.
- For employee-profile source rows, bank fields are removed from `details_json` only after an encrypted source payload is inserted, in the same transaction. The archival payload keeps legacy status and unknown bank-record fields encrypted. Import run and source-row ledgers are append-only; bank account events record the authenticated ADMIN and import time.
- Isolated Rust tests cover preview non-mutation/PII redaction, encryption, quarantine, pending reset, profile cleanup, hash/confirmation/key failures, idempotency, masked quarantine listing, duplicate-safe adoption and immutable adopt/dismiss audit. ADMIN review can map an active canonical employee, correct source values without mutating the archive, and create only pending accounts; dismissal retains its encrypted source. No production or user localStorage data has been read/imported. Backup/restore and disposable-copy operator verification, authorized key provisioning, and any live import remain open; a green unit suite does not authorize production migration.
