# Migration decisions and deviations

## Confirmed target architecture

- Keep the current workspace architecture: Rust/Axum backend, shared Rust `egui`/`eframe` UI, native desktop and WebAssembly canvas.
- Keep `legacy/` read-only and retained as reference.
- Do not introduce another UI framework or a DOM-based business frontend during this migration.
- Keep the WebAssembly UI on the chosen egui canvas. Legacy screenshots are visual acceptance references: matching layout, spacing, color, density and interaction is separate work from porting functionality or compiling the canvas. Track screenshot review per route, viewport and meaningful UI state; do not claim complete visual parity from a successful build alone.

## Admin leave-request identity and legacy compatibility

- New ADMIN rows in the legacy-compatible `leave_requests` / `employee_leaves` collections must select an active, non-retired HR employee. The server resolves and snapshots employee ID, code, name and department; client-supplied display fields are not authoritative.
- Once a row exists, its employee link and snapshot identity are immutable. Old rows without `employeeId` remain unlinked and ADMIN-readable/reviewable; status changes are allowed only while the historical name/code/department fields remain unchanged. Do not bulk-link free-text history unless a separately reviewed import proves an unambiguous mapping.
- This additive `employeeId`/`employeeCode` contract is a deliberate integrity safeguard. Existing legacy aliases and unknown JSON properties remain preserved; no legacy files or data are rewritten by this UI/API change.

## Initial source findings requiring explicit treatment

1. `legacy/web/src/modules/admin/AdminUsersModule.tsx` derives `twoFactor: false` and `lastLogin` placeholders when loading users; the list has a success-only Excel export message and a print-card success message without a corresponding real export/print implementation in that component. These are not verified capabilities and must not become fake Rust features.
2. The legacy user form displays several privilege labels, but its create handler maps only `Super Admin` to `ADMIN` and maps other labels to `USER`. The current Rust `users.role` schema accepts only `ADMIN` and `USER`. Distinct RBAC roles must not be claimed without finding and testing actual legacy authorization rules.
3. The current Rust admin users screen has hard-coded accounts and locally toggles active state; this is a confirmed parity defect. The first implementation slice replaces it with API-backed behavior.
4. Legacy docs describe SQLite and PostgreSQL; the current Rust backend is SQLite-only. No support mode is removed until the actual legacy deployment contract is reconciled and an explicit migration decision is recorded.
5. Rust dashboard metrics must come from backend data. Employee counts exclude `ADMIN` accounts and month grouping uses UTC, matching the legacy API's ISO month prefix. Monthly revenue/expense now use completed persisted cash vouchers; audit activity and aggregates over other unmigrated business sources remain unavailable until those schemas/events are migrated. Zero values or synthetic logs must not masquerade as complete data (`BLK-005`).

6. Admin system broadcast records may be migrated as drafts, but the Rust UI must not claim that Email, SMS or employee in-app delivery succeeded until a real sender/fan-out implementation returns verified delivery results. This follows the master migration prompt's prohibition on fake success; it is not approval to remove delivery features. The legacy page's caught-and-ignored email failures are documented as non-parity behavior, not copied.
7. `system_broadcasts` remains stored in the existing generic collection for shape/data compatibility, while typed ADMIN-only routes validate create/update/delete behavior. New rows use `Nháp` and zero read/recipient metrics rather than legacy's estimated sent/read numbers. Employee reads of the scope are denied at both typed and generic list routes because this is an admin campaign dataset.
8. Do not reproduce the legacy `GET /system/email-config` response, which includes the decrypted SMTP password. A Rust public DTO may expose only a configured/masked indicator; saving a blank password may retain the encrypted value server-side. Require a dedicated mail-encryption key and never fall back to the JWT signing key. Partial SMTP delivery must produce truthful per-recipient outcomes rather than HTTP success that hides failures.
9. The legacy activation template editor's HTML promise does not match its server renderer: the backend escapes `heading/body/buttonLabel/footer` before assembling activation email HTML. The migration must preserve this evidenced behavior or get an explicit product decision before enabling markup; client-side preview sanitization alone is not a security boundary.
10. Meeting-room data continues to use legacy-compatible `meeting_rooms` and `room_bookings` scopes in `collection_records`, but all writes go through typed ADMIN-only endpoints. Generic reads are also ADMIN-only and generic writes are blocked so room uniqueness, capacity and booking-overlap rules cannot be bypassed. Confirmed bookings are checked and inserted in an immediate SQLite transaction; cancellation preserves unknown legacy JSON fields. The legacy's hard-coded completed-history rows, local-only settings, and success-only export/provider switches are not migrated as if they were persisted capabilities.
11. Workflow blueprints retain the compatible `workflow_blueprints` collection shape but use typed ADMIN-only list/create/status routes; generic writes are blocked. A blueprint's “Đang áp dụng” status means only that it is enabled in the catalog. It does not create a running workflow, approval inbox, SLA scheduler or PKI signature. Do not carry over the legacy's fabricated `passRate: 100`; new catalog records begin with zero counters and the UI identifies execution metrics as unavailable.
12. Workflow request approval history must be persisted server-side and must identify the actual actor and decision time. The legacy request UI creates a fixed fake attachment, accepts a default PIN, and manufactures certificate IDs, hashes and success claims; its history verifier and exports also return toast success without verification/artifacts. These are defects, not a valid provider contract. Implement ordinary approval separately from qualified digital signing; PKI-required steps cannot be represented as signed until a real authorized CA/TSA integration is specified and verified (`BLK-008`).
13. The current server has only `ADMIN` and `USER`, with no persisted workflow approver assignment or department-role mapping. Until that model exists, workflow list/create/ordinary decisions remain ADMIN-only, an ADMIN cannot decide a request they created, and blueprint `roleRequirement` is descriptive rather than an authorization grant. Ordinary approvals are explicitly unsigned; any PKI-required step fails closed. Employee self-service, true approver resolution and return/resubmission must not be enabled by trusting requester text or UI role labels.
14. CRM contacts may be transferred only from an explicitly selected, approved SQLite copy through the allowlisted `crm_contacts` exporter; do not inspect deployment `.env`, tokens, or live production databases. The Rust importer preserves stable contact IDs/codes/timestamps, but deliberately replaces the legacy creator with the authenticated importing ADMIN, decrypts and re-encrypts PII with the configured CRM key, and archives the complete source record encrypted. Imported contacts are unverified until an operator reviews them. Preview remains summary-only; production import still requires key provisioning, backup/restore rehearsal and separate operational authorization.
15. Finance bank-account `account_number` values must retain the legacy finance-domain envelope format and remain encrypted at rest. ADMIN list/create may return the decrypted number as the legacy contract does; missing keys must fail closed. The `balance` field is only the declared opening balance, not a bank-verified available balance. Randomized ciphertext cannot enforce duplicate plaintext uniqueness, so Rust checks decrypted values inside an immediate transaction.
16. Never preserve the legacy internal-transfer sequence as two independent writes. Rust uses ADMIN-only `POST /api/v1/finance/bank-transfers` to insert the linked transfer record and paired debit/credit vouchers in one immediate transaction; it rolls back both sides on failure and uses an actor-scoped idempotency key for retries. `opening_balance` is user-declared, not live bank data, so this operation does not claim to validate available funds. The static e-banking provider switches and statement-upload toast remain unavailable, not real integrations/imports.

These decisions are provisional implementation safeguards. Product-level approval is still needed for delivery channels/provider configuration and actual scheduling/analytics behavior; see `BLK-006`.

## Attendance shift catalog — compatibility implementation, verification pending

- Legacy source: `ShiftsModule.tsx` loads `attendance_shifts` and saves its complete cached array with `PUT /collections/attendance_shifts`.
- Rust UI follows that contract: it first loads the current collection, then sends `{records: [...]}` with `PUT` when creating a shift. The backend preserves legacy camelCase and unknown JSON fields, uses `key` before `id` for collection identity, validates every record and duplicate key before opening the replacement transaction, and atomically replaces the collection.
- Compatibility risk: this is a full-snapshot write, so two concurrent administrators can overwrite one another's changes. A revision/ETag or optimistic conflict guard remains open. Persisted generic audit-event parity is also not implemented. Legacy localStorage/database records have not been imported.
- Status: HTTP method and payload shape now match the legacy UI, but `ATT-SHIFT-CATALOG-001` remains `IN_PROGRESS` until tests/build/runtime, concurrent-write protection, audit behavior and data transfer are addressed or explicitly scoped.

## Attendance leave requests — ADMIN flow and employee self-service are separate

- Legacy admin source `LeaveRequestsModule.tsx` reads and replaces `leave_requests`; the generic collection actor rule makes that scope ADMIN-only. Rust keeps that collection ADMIN-only and validates record shape, date ordering, half-day increments, status values, unique keys/codes and record size before writes.
- Legacy employee source `EmployeeLeavesModule.tsx` calls the cache-backed `dataService`; its first `leave_requests` request is ADMIN-only, while fallback `employee_leaves` is allowed for USER and the legacy generic API filters USER reads/replacements by `owner_id`. The component derives identity from `localStorage` with fallback identity, computes a fixed 12-day quota and may report success even if one mirrored write fails. Do not copy those client-derived values as authoritative. The Rust generic `collection_records` model remains ownerless, so the legacy-named generic scopes remain ADMIN-only for all Rust callers.
- Decision: store new self-service requests in dedicated `employee_leave_requests` rows keyed to `users.id`, and snapshot the linked HR employee code/name/department at submission. Require an active employee profile; reject client identity fields; keep old generic collection records untouched. This avoids widening access to global collections or silently reshaping historical records. Use transactional one-time ADMIN decisions and append-only `employee_leave_request_events`; only the owner and ADMIN may read events.
- The shared egui self-service view is now routed at `/employee/leaves`; the ADMIN attendance screen also lists and decides typed employee submissions while retaining the legacy generic collection view. No annual balance, automatic attendance deduction, print/export artifact or multilevel approver claim is made. Remaining risks: no historical import, no policy-backed balance/deduction, generic ADMIN collection writes still have stale-snapshot risk, and runtime tests are unavailable. Keep both leave features `IN_PROGRESS` pending test/build/runtime and import review.

## Employee overtime self-service — separate request workflow from payroll

- Legacy employee source `EmployeeOvertimeModule.tsx` provides date, hours in 0.5 increments, day category, project and reason, but resolves employee identity from client storage. Legacy admin overtime calculation uses a hard-coded hourly rate and displays a monthly-cap rule without an authoritative payroll or attendance source.
- Decision: store new requests in `employee_overtime_requests` keyed to the authenticated user and snapshot HR identity server-side. Keep the legacy category labels as request classification only; do not apply multipliers, estimate money, claim approved hours as actual attendance, or enforce the legacy monthly-cap assertion as payroll policy.
- ADMIN decisions are one-time and paired transactionally with immutable actor/time/status/note events. Users can only list their own requests and both owner/ADMIN can read request history. Generic attendance collection access remains ADMIN-only.
- Preserve the audited legacy input contract: a 0.5-hour minimum/step and no upper bound in this form. Do not add a payroll/monthly cap without a verified policy. No historical data is imported by this slice.
- Status: source implementation only; Rust tests/build/runtime and data import are pending (`BLK-007`, `BLK-009`).

## Attendance shift assignments — link new schedules to real HR and shift records

- Legacy source `ShiftAssignmentModule.tsx` stores assignment rows in the ADMIN generic collection, accepts employee name/code/position/department as text, and fabricates an employee code when omitted. The pending swap decision branch has no source UI that creates a swap request; its status changes are local collection mutations without a server actor record.
- Decision: new typed assignments require an active non-ADMIN user plus linked active employee profile and an active `attendance_shifts` entry. The server snapshots HR identity and shift fields, validates the effective period, and records creation actor/time in an append-only event table. Assignment records are not inferred from client-provided names.
- The legacy collection remains ADMIN-readable for a future dry-run/import review, but all generic mutations for `attendance_shift_assignments` are blocked to prevent bypassing the typed contract. No old rows are copied or deleted in this slice; unresolved/fabricated identities must be reported rather than guessed during import.
- Do not reproduce the legacy FaceID sync, 24/7 coverage/SLA, Excel-success or unreachable client-only swap approvals as working features. This module exposes no evidence-backed edit/end action. Status remains `IN_PROGRESS` until import, Rust tests/build/runtime and web/native persistence checks pass (`BLK-007`, `BLK-009`).

## Task assignment — resolve manager scope on the server

- Legacy task UI derives the current employee's department, directly managed units and one-level child units, then presents eligible assignees. Client caches and fuzzy name matching are not authorization evidence.
- Decision: keep ADMIN organization-wide. For USER, build `/tasks/assignees` options from the authenticated account's linked HR profile, exact department tokens, exact manager identity fields on org units and one-level child-unit manager rules. A child unit with a distinct manager exposes only that manager; otherwise eligible unit members are listed. Exclude inactive and retired accounts.
- `POST /tasks` and `POST /tasks/batch` repeat the same scope resolution inside their write transaction; submitted project and every assignee must be in the server-derived options. Resolve assignees by stable user ID or employee code, never ambiguous name/email. Batch creation accepts at most 1,000 assignees, rejects duplicate canonical users, and creates all per-assignee tasks, checklist rows and activity records atomically. UI filtering is only an affordance, not the security boundary.
- The manager/child-unit and batch authorization/rollback cases pass in the Docker Rust 1.89 workspace suite. `TASKS-001` remains in progress: historical import, native/browser end-to-end and full parity remain open.

## Decision process

For each deviation, record source evidence, security/data impact, alternatives, compatibility plan and approval status. Do not infer approval from a successful build or a placeholder screen.

## HR certificate identity, status and unsupported actions

- Source: `legacy/web/src/modules/hr/CertificatesModule.tsx` creates a time-derived employee code when the form omits one, assumes company sponsorship and an 8,000,000 VND fee, and synthesizes a Credly URL from the credential ID. The “copy” button, report export and recertification-funding action only show success messages; no clipboard operation, export artifact, funding record or issuer verification is implemented in that screen.
- Decision: require an employee code that resolves to a non-ADMIN HR profile, and snapshot employee ID/name/code/department from the server. Keep code generation for the certificate record only. Require the operator to explicitly mark sponsorship and enter its amount; do not create a default verification URL. Derive status from expiry at read time rather than trusting a stale saved label.
- The Rust view may open/copy a supplied HTTPS URL but identifies it as issuer-provided and not externally verified. It does not claim a generated report, recertification approval/payment or verification result. Existing compatible collection records remain available through the typed ADMIN route; legacy localStorage import is a separate reviewed operation.
- This is a data-integrity/security safeguard, not an approved removal of a verified external integration. A real issuer API, export format or recertification approval policy must be specified and tested before those claims are enabled.

## HR uniform identity and handover evidence

- Source: `legacy/web/src/modules/hr/UniformsModule.tsx` synthesizes a holder code when missing, sets a future delivery date during creation, and writes a receiver-signature sentence during ADMIN handover without collecting a receiver action. Its 120-piece stock metric and expected delivery timing are hard-coded; export only shows a success toast.
- Decision: resolve new requests against a real HR profile, snapshot holder identity from the server, and assign request date/code there. Only record a handover after explicit confirmation by ADMIN, with actual administrator actor/time; describe it as an admin handover record, never as the employee's signature or proof of receipt. Generic mutations are blocked and repeat handover is rejected.
- Do not display stock availability, promise delivery dates or claim Excel output until there is a persisted inventory/scheduling/export contract. Existing compatible records remain readable through the typed ADMIN route; localStorage import requires a separate review.

## HR onboarding: distinguish persisted records from the visual checklist

- Source: `legacy/web/src/modules/hr/OnboardingModule.tsx` persists only the initial create through the generic collection. It invents employee codes, starts at progress 15%, sets `laptopProvided`/`emailCreated` true, and stores a fixed current step. The five checklist checkmarks are derived from this number. The completion button updates React state only and reports contract approval without an API request or contract record.
- Decision: new onboarding records must link to actual HR employee and mentor profiles and snapshot server-owned identity. Preserve the legacy 60-day evaluation-date calculation. Do not seed progress, device/account provisioning, checklist state, signed-contract state or completed status; do not expose a completion action until those operations have persistent contracts and authorization rules.
- The shared UI retains checklist topic descriptions but labels their state as unavailable. A real milestone model, provisioning integration and probation/contract decision remain separate required work, not inferred from legacy display text.

## HR recruitment: separate job openings from the absent candidate pipeline

- Source: `RecruitmentModule.tsx` persists opening create/list only. Applicant/interview/offer counters are seeded at zero with no mutation path; acceptance/time-to-hire cards and export/copy/CV actions are static or toast-only.
- Decision: migrate the actual opening record fields to an ADMIN-only typed API; make key, initial status and creator server-owned; validate unique job codes and dates; block generic collection bypass. Do not interpret the seeded zeros as real candidate totals or report static funnel KPIs.
- A candidate data model, privacy/retention rules, interview/offer decisions and hiring outcome semantics need an explicit contract. Until then the Rust UI shows the saved opening and clearly says candidate data and transitions are unavailable.

## HR headcount: derive actual staffing and do not imply approval

- Source: `HeadcountModule.tsx` persists quota rows but accepts caller-provided `actual`, vacancies and status; its form defaults those fields to synthetic values and falls back to browser localStorage. No edit or quota-approval writer was found in this module.
- Decision: accept quota and a clearly labeled planned monthly budget, but derive actual staffing on the server from active, non-retired/non-pending employee profiles with matching department and position. Recompute vacancy/status; ignore caller-supplied derived fields. Keep the generic collection scope behind the typed ADMIN API.
- The static “approved by board”/fill-rate wording is not evidence of approval. Confirm approval authority/versioning and department/position catalog sources before adding those workflows; do not treat this planning budget as payroll.

## HR rewards: enforce workflow order without claiming legal signature or receipt

- Source: `RewardsModule.tsx` persists award creation/list, but the status update is a generic client write and the award action can skip approval. Employee identity and signer fields come from browser state. Static eNPS/fund totals and toast-only PDF/book export are not treated as real data/actions.
- Decision: resolve employee recipients from active HR profiles; require explicit fields for team recipients; validate unique reward code/decision; block generic writes. Enforce pending → approved → awarded as one-time ADMIN-recorded transitions with actor ID/time in append-only events.
- Preserve legacy status values for storage compatibility, but label “Đã ký quyết định” as an admin-recorded approval only when a corresponding server event exists. Ignore legacy JSON audit-shaped fields; a legacy status cannot authorize the award transition. The award transition is not payment proof or recipient acknowledgment. Digital signing, multi-role approval, evidence attachments, safe import and retention policy require separate contracts.

## HR performance reviews: separate entered scores from fabricated analytics

- Source: `PerformanceReviewModule.tsx` persists review create/list and status update, but the client supplies employee/evaluator identity, status, synthetic 54/18/18 pillar scores and default bonus; the approval toast claims payroll payment. Static average/progress/promotion/360 claims and export do not establish real policy/data.
- Decision: resolve new employee identity and evaluator on the server; accept only explicit self/manager score, period, code, declared proposed bonus and comment; validate scores and derive grade in Rust. Store typed create/approval actor/time in append-only events, block generic scope reads/writes and disregard legacy client-supplied actor/verification fields.
- “Complete” means only that an ADMIN recorded completion; it does not trigger payroll or prove payment. Old rows without typed ledger events remain visible as unverified and require a reviewed import/adoption process before approval. Confirm scoring/grade rules and payroll integration before adding 360 pillars, promotion or paid-bonus claims.

## HR employee history: distinguish an entry from an approved personnel decision

- Source: general history rows are only held in React state; the module's bank account tab uses a generic collection/cache and its identity tab treats profile/localStorage fields as eKYC presentation. Request/export controls do not perform those actions.
- Decision: persist only explicit history notes in a typed ADMIN API, resolve employee code against an HR profile, assign recorder/time on the server and make rows append-only. A declared signer remains unverified, and storing a note does not approve a decision or change an employee's actual employment status.
- Bank account management now uses dedicated employee-owner and ADMIN APIs, canonical directory identity, pending-by-default creation, encrypted sensitive fields, masked UI, one-time audited transitions and a blocked generic-collection path. Strip/reject bank values in employee profile details to prevent plaintext bypass. The importer leaves generic collection rows intact; when profile bank fields are actually applied, it archives those fields encrypted before scrubbing them atomically. No production import has run. Treat legacy status/identity as untrusted and require reviewed reconciliation; production key provisioning is required and missing keys fail closed.
- The bank import slice now has a read-only localStorage exporter and ADMIN preview/apply flow. Apply binds to a digest of the uploaded bundle plus current generic/profile sources and directory resolution, requires exact confirmation, preserves source payloads encrypted, sends unresolved/duplicate values to encrypted quarantine, resets all imported decisions to pending, and removes bank fields from employee profile details only within the same successful transaction as their encrypted archival. The generic legacy collection and the legacy web code remain unchanged. No production data import is authorized or performed by this implementation.
- Do not derive verified eKYC state from browser storage/profile fields without an actual provider and verifiable evidence contract.

## CRM PII storage compatibility

- Source: `legacy/api/crypto.mjs` uses a CRM-domain HKDF-SHA256 subkey and an AES-256-GCM `ENC:` envelope for phone, email, address and bank account. The backend reproduces that envelope and key parsing behavior; a fixed ciphertext generated with Node's built-in crypto verifies cross-language decryption.
- Rust accepts the master key from `KIYOVN_MASTER_KEY`; it reads `.kiyovn-master.key` only from an explicitly configured `KIYOVN_DATA_DIR`, and does not create or generate key files. Without key material, writes fail with 503 and encrypted PII reads fail closed. Plain legacy values remain readable; corrupted ciphertext is never returned as plaintext.
- No key material was read or printed during implementation; the interoperability test uses an artificial constant key only in test code. Existing legacy CRM records remain untouched and unimported. Before data transfer, confirm the authorized key/version through deployment secret management and run a dry-run importer against a disposable copy.
- Status: compatibility implementation and isolated tests are complete; production key provisioning, source-data import and UI runtime acceptance are not verified.

## CRM local history import: preserve evidence, not browser assertions

- Scope is deliberately limited to the two observed browser caches `crm_supplier_evaluations` and `crm_feedback`; contacts and other CRM scopes are not part of this importer. `legacy/` and its localStorage are read-only.
- Downloaded feedback exports may contain plaintext personal data. The exporter reads only those keys, logs only metadata/counts, and never mutates storage or contacts the network. Admin preview returns only counts/digests; transfer and temporary-file handling remain operator responsibilities.
- Imported evaluation totals/tiers are recomputed from validated dimensions. Browser resolution state, resolver and timestamps are retained only in the encrypted source archive; imported feedback returns to pending. Both record types are marked unverified for human reconciliation.
- Apply requires the configured CRM encryption key, a current target/bundle digest and exact confirmation. Typed rows, encrypted raw source, and append-only audit run commit atomically; exact re-export is idempotent and changed data under the same source key conflicts. Only synthetic fixtures were used; no live import is authorized or performed.
